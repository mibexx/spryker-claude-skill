# Template publisher-and-synchronization

Write side (Publish & Synchronization) and read side (Client) for the running example **ProductBadge**: change to `spy_product_badge` -> entity event -> publisher plugin -> writer -> `spy_product_badge_storage` -> synchronization behavior -> sync queue -> Redis -> `ProductBadgeClient`. Background: [Publish & Sync](../../references/07-publish-sync.md), [Client/Storage](../../references/08-client-storage-search.md). Prerequisite: schemas and transfers from [transfer-and-propel](../transfer-and-propel/README.md), source module from [zed-module](../zed-module/README.md).

## Fixed names

| Item | Value |
|---|---|
| Resource name | `product_badge` (identical in schema, trigger plugin, sync plugin, key builder) |
| **Storage key** (Redis, code without internal prefix `kv:`) | `product_badge:<id_product_abstract>`, e.g. `product_badge:123`. Generated by the `SynchronizationService` (`DefaultKeyGeneratorPlugin`), reference = `fk_product_abstract`, no store/locale. Directly in Redis: `kv:product_badge:123` |
| Redis value | JSON of `ProductBadgeStorage`: `id_product_abstract`, `product_badges[]` (+ `_timestamp` from the behavior) |
| **Entity events** (event behavior on `spy_product_badge`) | `Entity.spy_product_badge.create`, `.update`, `.delete` |
| **Publish event** (regeneration) | `ProductBadge.product_badge.publish`, event ID = product abstract ID |
| Publish queue | `publish.product_badge` (array key in the plugin stack) |
| Sync queue | `sync.storage.product_badge` |
| Queue pool | `synchronizationPool` (schema parameter `queue_pool`, constant `PRODUCT_BADGE_SYNCHRONIZATION_POOL_NAME`) |
| Constants | `Pyz\Shared\ProductBadgeStorage\ProductBadgeStorageConfig` |

Writer flow: entity events deliver the product abstract ID as a foreign key (`spy_product_badge.fk_product_abstract`, stored in `foreignKeys` by the event behavior). The writer loads all badges per product abstract and writes exactly **one** storage row per product abstract. Without badges the row is deleted (`delete()` removes the Redis key).

## Placeholders / customization

- Replace `ProductBadge` / `product_badge` with your own module name (module `<Name>Storage` in Zed, Client module `<Name>`).
- The writer reads the source table via `SpyProductBadgeQuery`, which is injected via `providePersistenceLayerDependencies()` (pattern from `ProductAlternativeDependencyProvider::PROPEL_QUERY_PRODUCT`). Alternative: obtain the source module's Facade directly via the locator (no bridge in the project, see [Reference 02](../../references/02-project-module.md)).
- **No bridges:** the Facade `EventBehavior` (Zed) as well as `StorageClient` and `SynchronizationService` (Client) come directly from the locator (`$container->getLocator()->storage()->client()` etc.). The Factory getters are typed to the foreign modules' interfaces (`EventBehaviorFacadeInterface`, `StorageClientInterface`, `SynchronizationServiceInterface`).
- With a store- or locale-dependent key: add the `store`/`locale` parameter in the schema, set `setStore()`/`setLocale()` on the `SynchronizationDataTransfer` in the reader, `hasStore()` in the sync plugin to `true`.
- Queue pool (`queue_pool`) only without a `store` parameter. It is **required** here: `Behavior` sync also runs without it, but without `getSynchronizationQueuePoolName()` `sync:data` throws the `SynchronizationQueuePoolNotFoundException` ("You must specify either store column or `SynchronizationQueuePoolName`"). Schema parameter, plugin return value and `RabbitMqConfig::getQueuePools()` must use the same pool name (`synchronizationPool`).
- For Search instead of Storage: table `*_search`, `SynchronizationSearchQueueMessageProcessorPlugin`, `params` `{"type":"page"}` (see [Client/Storage/Search](../../references/08-client-storage-search.md)).

## Commands afterwards

All commands ran in shop 202610.0 with exit 0 `[live verified (202610.0)]` (registration as described above, `queue:setup` created `publish.product_badge`, `sync.storage.product_badge` and the `.error` queues, `event:dump:listener` shows `ProductBadgeStorage::ProductBadgeWritePublisherPlugin` with "Handled in Queue: Yes").

```bash
docker/sdk cli console transfer:generate
docker/sdk cli console propel:install          # generates entities incl. event/synchronization hooks
docker/sdk cli console queue:setup             # creates publish.product_badge and sync.storage.product_badge
docker/sdk cli console event:dump:listener --event=Entity.spy_product_badge.create   # dev console commands only
docker/sdk cli console publish:trigger-events -r product_badge       # regeneration (mirror table anew)
docker/sdk cli console sync:data product_badge                       # re-sync to Redis (arguments, no options)
docker/sdk cli console queue:worker:start                            # details: ../../references/22-console-cron-queue.md
```

Check: save a badge in the Back Office/via the Facade, let the workers run (in the shop the scheduler does this within one minute; otherwise `queue:task:start event`, `queue:task:start publish.product_badge`, `queue:task:start sync.storage.product_badge`), then check `spy_product_badge_storage` (row with `data`, `key = product_badge:<id>`) and Redis (`valkey-cli -n 1 get kv:product_badge:<id>`, database 1 = Storage).

Observed live (202610.0): (1) data import (`data:import:product-badge`, publish event via `PublishAwareStep`) -> storage rows and Redis keys `kv:product_badge:4/5`. (2) Creation in the Back Office and via Glue Backend (entity event `Entity.spy_product_badge.create`) -> publisher -> storage row -> Redis. (3) Deletion via Propel (`SpyProductBadge::delete()` plus `EventBehaviorFacade::triggerRuntimeEvents()` in a script) -> storage row and Redis key disappear. (4) `sync:data product_badge` rewrites missing keys (the value then contains no `_timestamp`). **Important:** `publish:trigger-events -r product_badge` changes nothing if the source record is unchanged (Propel does not save the unchanged storage row, no sync message is created). A manually deleted Redis key therefore only comes back via `sync:data product_badge [<id_product_abstract>,...]`. If source rows are deleted via SQL, no entity event is created, and the trigger only reads existing source rows: the storage row and key remain.

## Notes and deviations

- `handleBulk(array $eventEntityTransfers, $eventName): void`: the parameter type of `$eventName` stays untyped (interface `EventBulkHandlerInterface`, typing it would be a signature violation), `: void` is compatible.
- Direct sync is off in the release (`isDirectSynchronizationEnabled() = false`, and in addition it only applies with `SPRYKER_DYNAMIC_STORE_MODE`). The template works with queue sync.
- The sync ID arguments of `sync:data product_badge <ids>` are product abstract IDs (filter on `fk_product_abstract` of the storage table).
- No transaction bracket around the loop in the writer. For atomicity add `$this->getTransactionHandler()` in a business class [Assumption, not checked].
- `ProductBadgeStorageRepository::getProductBadgeEntityTransfers()` deliberately returns `SpyProductBadgeEntityTransfer` (via `buildQueryFromCriteria()`): `EventResourceRepositoryManager` reads the ID column via `modifiedToArray()['fk_product_abstract']` from the trigger plugin's return value. If you map to `ProductBadgeTransfer`, `publish:trigger-events` fails with a `TypeError` in the mapper (`SpyProductBadge` expected, `SpyProductBadgeEntityTransfer` passed). `buildQueryFromCriteria()` always returns entity transfers, never Propel objects.
- The event behavior on the source table uses `column="*"`. A DB-side `ON DELETE CASCADE` would not trigger any entity events (therefore not set in the schema).
